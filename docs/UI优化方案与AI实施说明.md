# KC-PAY-GPT 前端 UI 优化需求与 AI 实施交接文档

日期：2026-11-09

## 1. 任务与设计方向

为现有 KC-PAY-GPT 优化用户前台、管理后台、后台登录页和订阅查询页。用户明确希望采用「苹果那样的白色、透明、玻璃」风格。

交付应是一套白色为主、通透克制、层级清楚、可日常使用的界面。借鉴 Apple 界面的留白、排版、材质和交互节奏，不复制 Apple Logo、品牌资产或产品页面。保留 KC 自身品牌，不暗示本服务属于 Apple 或 OpenAI 官方。

本文是实施建议和交接规格，不表示任何尚未实施的功能已存在。优先级和参数为作者建议，实施 AI 可在不改变业务行为的前提下微调。

## 3. 方案选择

用户已确定视觉方向，技术实施建议选择 B。

| 方案 | 范围 | 得失 |
| --- | --- | --- |
| A. 仅换皮 | 调整配色、圆角、阴影和字体 | 改动小，但保留信息拥挤、流程层级不清的问题 |

## 4. 视觉设计系统：白色玻璃

### 4.1 总体观感

- 背景以暖冷中性的浅灰白为主，可放置极淡的蓝色、银灰色大面积径向渐变。
- 玻璃感来自“半透明表面 + 背景模糊 + 白色高光边缘 + 极浅投影”，不能仅靠降低整个元素的 opacity。
- 导航、顶部工具条、浮层可明显通透；表单、表格和长文本区域应有更实的白色底。
- 不堆叠多层模糊；不用深色科技背景、大面积彩色光团、过量胶囊、霓虹描边或持续漂浮动画。
- 一个页面只有一个主要视觉焦点。用户页焦点是兑换操作，后台焦点是数据和任务。

### 4.2 建议变量

```css
:root {
  --bg-page: #f5f5f7;
  --surface-solid: #ffffff;
  --surface-glass: rgba(255, 255, 255, 0.76);
  --surface-glass-strong: rgba(255, 255, 255, 0.92);
  --text-main: #1d1d1f;
  --text-secondary: #515154;
  --text-muted: #6e6e73;
  --primary: #0071e3;
  --primary-hover: #0066cc;
  --border: rgba(60, 60, 67, 0.14);
  --glass-highlight: rgba(255, 255, 255, 0.85);
  --success: #187a3d;
  --warning: #945600;
  --error: #c52b25;
  --radius-control: 12px;
  --radius-card: 22px;
  --radius-dialog: 26px;
  --shadow-card: 0 8px 32px rgba(31, 38, 50, 0.06);
  --shadow-dialog: 0 24px 80px rgba(31, 38, 50, 0.16);
  --glass-blur: 20px;
}
```

这些是起始值，不替代实际对比度检查。旧变量仍被内联样式引用时，保留兼容别名，不能直接删除。

玻璃表面使用 `backdrop-filter: blur(20px) saturate(140%)`，包含 `-webkit-backdrop-filter`。不支持时通过 `@supports` 回退为接近不透明的白色。不要对整页或整张长表格应用模糊。

### 4.3 排版与尺寸

- 字体优先系统栈：`-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif`。不下载或随包分发 Apple 专有字体。
- 正文 14–16px；辅助文字 12–13px；后台页标题 26–30px；前台主标题 36–44px，手机端 28–32px。
- 字重以 400/500/600 为主，减少整页粗体。
- 间距采用 4/8/12/16/24/32/48px，表单内部间距 16–20px，卡片内边距 24–32px。
- 输入和主按钮高度 44–48px；触控目标至少 44px；图标 16–20px，使用已有图标体系。
- 常规动效 160–220ms；支持 `prefers-reduced-motion`；键盘焦点始终可见。

## 5. 用户兑换页

### 5.1 布局

桌面端：顶部轻量玻璃导航；主体最大宽约 1080px，左侧简明介绍与帮助，右侧约 520–600px 的兑换卡片。手机端单列，兑换操作放在介绍和套餐说明之前。

首屏应优先看到标题、当前步骤、CDK 输入与主按钮。现有三张套餐介绍卡片降为次级说明，可放在主操作之后。不要让用户先滚动一屏广告才看到输入框。

导航仅保留品牌、状态查询、订阅查询/帮助等真实可用入口。客服入口沿用已有真实配置，不编造联系地址。

### 5.2 兑换流程

1. 输入 CDK：明确标签、格式提示、校验中、无效/已使用/冷却等反馈。
2. 提交 Session：展示服务端确认的套餐信息；提供三步获取说明和获取链接；强调 Session 是敏感登录凭据。
3. 查看结果：独立任务状态面板，展示业务状态、更新时间和下一步操作。

第三步是 UI 对现有任务状态的组织，不增加新的后端业务阶段。沿用现有“查询恢复任务”的能力；不要求存储完整 Session 到浏览器。

Session 输入框禁止自动提交、禁止写入 URL、日志或新增本地持久化。默认可用遮挡摘要展示已填内容，允许用户主动编辑原文；不能因遮挡导致 JSON 被截断或提交值变化。粘贴不触发付款，主按钮明确写“确认开通”。

### 5.3 任务与异常状态

- 覆盖待输入、校验中、校验失败、可提交、提交中、处理中、成功、业务失败、网络异常和连接恢复。
- 提交中禁用重复点击；切换页面、重新渲染时不重复创建任务。
- WebSocket 断线只显示“连接中断，正在恢复”，不能推断充值失败，也不能自动重新提交开通。
- 使用服务端真实状态映射步骤。没有实际进度数值时用阶段指示，不显示虚构的 80%、倒计时或保证完成时间。
- 错误用通俗摘要，技术详情按需展开；不能暴露 Session、卡号、CVC、代理凭据。
- 成功页只展示后端确认的信息。失败页提示状态查询或已有客服渠道，不承诺自动退款或已回滚。

### 5.4 文案

统一简体中文；主按钮、错误提示和返回动作风格一致。删除或改写未经证实的“极速”“必定成功”“3–5 分钟开通”“失败可回滚”等保证。

当前页面存在具体模型权益、倍数额度和默认地区文字。UI 重做不得新增未经验证的产品权益；套餐名称、地区和币种优先使用现有接口真实数据。区分套餐地区、结算币种和实际账单地址，不把一个字段标成另一个概念。

## 6. 管理后台

### 6.1 全局框架

使用左侧约 232px 的半透明侧栏、顶部约 64px 的轻量工具栏和浅灰白内容区。侧栏可折叠；平板/手机改为抽屉。页面顶部显示标题、短说明和该页主要动作。

建议导航分组如下，展示名称可调整，原有页面标识、权限和处理函数需保留：

- 工作台：概览、任务管理、自动化任务。
- 业务资产：CDK、银行卡池、Session、账单记录、续费管理。
- 运行资源：浏览器池、代理池、账单地址、支付链接调试。
- 系统与安全：系统配置、运行日志、登录日志。

必须先从现有导航核对全部入口，以上不是允许删减功能的清单。受二次验证保护的页面继续先验证，不通过 CSS 隐藏代替权限控制。

### 6.2 概览

顶部保留 4–6 个最有用的指标，数值来自真实接口。优先展示运行任务、失败任务、可用资源与最近结果；具体字段以现有返回为准。

下方展示最近任务和需要处理的问题。没有历史时间序列接口时不画假趋势图；没有状态接口时不显示“服务健康”。

### 6.3 表格与操作

- 所有列表统一搜索/筛选区、表头、行高、状态标签、分页和操作按钮。
- 表格所在卡片使用不透明或高不透明度白底，禁止文字背后出现干扰性渐变。
- CDK、任务 ID 和卡号后四位使用等宽数字；金额右对齐并带原始币种，不能混币求和。
- 常用操作直接展示，低频操作收进更多菜单；不要仅用无标签图标表示删除。
- 超宽表格在容器内横向滚动，页面主体不横向溢出；移动端保留核心列和详情入口。
- 筛选、空结果、加载失败和未授权分别展示，不把请求失败显示为“暂无数据”。
- 删除、清空和批量破坏性操作使用明确确认弹窗，写清对象与数量。不要新增一键支付等高影响快捷操作。

### 6.4 任务、日志和资源

任务详情可使用右侧抽屉：基本信息、真实状态、时间、错误摘要、日志和已有截图/录像入口。已有查看能力应保留，抽屉可以按开发复杂度后置。

日志使用等宽字体，提供现有刷新/清空能力；若新增前端搜索、暂停自动滚动，必须清楚表明搜索范围仅为已加载日志。不要前端猜测日志等级或隐藏关键失败。

浏览器池页面把“当前模式、槽位占用、等待队列”放在前面，长篇技术备忘折叠到帮助区。明确浏览器池复用进程、每单隔离上下文；独立模式每单重新启动浏览器。不要改变运行模式开关实际行为。

### 6.5 系统配置

长配置页按第三方 API、并发维护、通知、验证服务、安全、支付地区等现有功能分区。每区有清楚的标题、说明和对应保存动作。

不要在 UI 重构时合并原本独立的保存接口。测试连接与保存配置分开；保存成功后以返回结果或重新读取确认。密钥默认掩码，禁止把占位掩码作为新值提交覆盖原密钥。

## 7. 登录页与订阅页

登录页：淡灰白背景、居中玻璃卡片、清楚的字段标签和错误提示。完整保留账号密码、二次验证、Telegram 验证、Token 清理和跳转逻辑。密码支持显隐，验证错误不清空无关字段。

订阅页：沿用同一导航与表单组件。根据现有 API 真正能力确定“订阅查询/发票助手”命名；没有发票下载接口时不新增虚假下载按钮。Session 输入和展示遵循与兑换页相同的敏感信息规则。

## 8. 可维护性与安全要求

- 新增共享设计变量文件，例如 `public/css/tokens.css`；页面专属 CSS 使用 `.recharge-page`、`.admin-page` 等作用域。
- 不用大批 `!important` 覆盖旧样式；逐段移除冲突规则，验证旧内联变量兼容。
- 迁移 DOM 前整理 `id`、`data-*`、内联事件、函数和页面选择器对应关系。不可引入重复 ID。
- 用户可控文本优先用 `textContent` 渲染；必须使用 HTML 时沿用可靠转义，不能在美化时引入 XSS。
- 保留已有银行卡加密和接口脱敏边界，不为详情展示返回更多敏感字段。
- 截图和演示只用虚构数据；不读取或提交真实 `.env`、Session、银行卡和数据库备份。
- 当前使用 Google Fonts 和 `lucide@latest` 等外部资源；新增界面应有字体/图标加载失败回退。若本地化资源，要固定版本并记录来源与许可，不直接复制未知资源。

## 9. 建议实施顺序

每阶段完成可审查的结果，再继续下一阶段：

1. 盘点：记录全部页面入口、功能、DOM 依赖、接口和状态；用测试数据保存改造前截图。
2. 建立视觉基线：共享变量和基础控件；先完成登录页及兑换页，展示桌面和手机效果。
3. 完成兑换状态、订阅页、错误反馈和键盘操作。
4. 建立后台导航与通用表格，优先改概览、任务、CDK、银行卡池、账单。
5. 逐页完成 Session、续费、资源、日志、调试与系统配置，核对无功能遗漏。
6. 浏览器实测、必要回归、整理截图和交付说明。

不得在页面样式未稳定前大规模搬迁业务脚本。若需要改后端或改变业务流程，另列建议和原因，不夹带进 UI 提交。

## 10. 验收清单

### 视觉与可访问性

- [ ] 桌面 1440px、笔记本 1280px、平板 768px、手机 390px 和 360px 下可用。
- [ ] 整体为白色玻璃风格，导航、卡片、输入框、弹窗和提示视觉一致。
- [ ] 正文对比度至少 4.5:1，大字及关键控件边界满足适用的 3:1 要求；不能只靠颜色区分状态。
- [ ] 手机无整页横向滚动；弹窗可滚动，关闭按钮和底部动作始终可到达。
- [ ] Tab 可访问所有操作；弹窗具有语义、焦点进入/返回及合理的 Escape 行为。
- [ ] 禁用透明模糊或开启减少动画后，内容仍清楚可用。
- [ ] 长邮箱、长错误、多位金额、空表格和大量日志不会撑坏布局。

### 业务回归

- [ ] CDK 有效、无效、已使用、冷却等状态处理保持正确。
- [ ] Session 缺失/无效、重复点击、接口超时、连接断开均有明确反馈。
- [ ] 任务成功和失败均基于服务端真实业务终态，连接恢复不产生新订单。
- [ ] 登录、二次验证、退出及权限过期流程正确。
- [ ] 后台所有原有页面仍可访问，筛选、分页、导入导出、复制和配置保存均可用。
- [ ] 密钥掩码不会覆盖真实值，敏感字段不新增泄漏。
- [ ] 浏览器控制台无新错误、资源无新增 404、事件不重复绑定。
- [ ] 在可用环境运行现有 `npm test`，记录实际结果；未执行项明确列出，不能声称已通过。

真实充值不是 UI 验收前提。使用隔离测试环境和模拟接口验证提交与状态流，不用真实付款来证明按钮有效，不执行数据库重置脚本。
